### Task 3: Kontrast messen, Prüfliste aktualisieren und abnehmen

**Interfaces:** Der neue Spec liest getComputedStyle an den realen Statusdarstellungen und ihren Hintergründen. Alpha-Mischung bis zur opaken Grundfläche auflösen; eine DOM-/Canvas-Farbauflösung auch für CSS-Funktionen verwenden. Keine Token-Sollwerte importieren.

Die unabhängige Leseanalyse grenzt den Kontrastteil auf StatusWahl/StatusTag in FahrzeugePage, PersonalPage und MaterialPage ein. EinheitDetailPage selbst rendert diese Statusfarben nicht. Die Karten liegen transparent auf dem Layoutgrund, die Tabellen auf Container-/Zellgrund. Der Test muss beide tatsächlichen Untergründe berücksichtigen.

Risikobeleg der Vorbereitung aus der Tokenrechnung, vor den unten dokumentierten Browsermessungen: alle fünf erreichbaren Rollenfarben liegen im Hellmodus unter dem Textziel 7:1; neutral liegt auf der dunklen Tabellenfläche bei etwa 4,92:1. StatusTag setzt dieselbe Rollen-/Freitextfarbe auf Text und Rand. Beliebiger Freitext kann die zwei Textkontrastziele nicht garantieren. Deshalb ist eine reine Ergänzung grüner Tests voraussichtlich nicht möglich.

Empfohlene minimale Korrektur bei bestätigtem RED: den Statuswortlaut mit token.colorText lesbar halten, kontrollierte Rollenfarbe auf Rand/Formzeichen mit mindestens 3:1 messen. Eine freie Mandantenfarbe bleibt nur dann ohne Kontrastgarantie, wenn sie ausschließlich redundante Dekoration ist und weder Wortlaut noch notwendige Begrenzung trägt; ansonsten braucht der betroffene Träger einen kontrastierenden Fallback. Diese Entscheidung im Code und in der Prüfliste genau begründen. Keine ganze Palette oder neue Statussemantik erfinden.

Seeding für die Kontrastmatrix: eigene Fahrzeug- und Personalstatus über POST /api/fahrzeug-status und /api/personal-status anlegen, jeweils eine Disposition über ihren PATCH-Endpunkt zuweisen. Materialzustände bilden die bereits im Code erreichbaren Rollen normal/bedien/alarm/achtung ab; neutral über einen neutralen Statusdarstellungspfad abdecken. Marke ist auf diesen Statusflächen nicht erreichbar und wird nicht künstlich hineingetestet.

Der mathematische Kern arbeitet auf browserseitig aufgelösten RGB-Werten:

```ts
type RGB = readonly [number, number, number];
function luminanz([r, g, b]: RGB): number {
  const linear = (wert: number) => {
    const s = wert / 255;
    return s <= 0.04045 ? s / 12.92 : ((s + 0.055) / 1.055) ** 2.4;
  };
  return 0.2126 * linear(r) + 0.7152 * linear(g) + 0.0722 * linear(b);
}
function kontrast(vordergrund: RGB, hintergrund: RGB): number {
  const a = luminanz(vordergrund);
  const b = luminanz(hintergrund);
  return (Math.max(a, b) + 0.05) / (Math.min(a, b) + 0.05);
}
expect(kontrast([255, 255, 255], [255, 255, 255])).toBe(1);
expect(kontrast([0, 0, 0], [255, 255, 255])).toBe(21);
```
